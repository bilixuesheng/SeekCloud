## 二、决定之间对不上的地方

**1. 归档：规格说"停止沙箱"，代码是删掉沙箱（中，已补评论 #37）**

规格 #13 和 #37 写的是"归档：停止沙箱……取消归档后恢复"。`Sessions.archive` 发的是 `destroy_sandbox`。现在只有假宿主机，看不出差别；接上真宿主机以后，归档一个回合还在跑、或者有改动还没推送的会话，改动就丢了。改成：归档时先停回合、照常补提交和推送，再停止沙箱（不删），照休眠的规矩 7 天后回收。

## 四、设计上的坑和漏掉的边界情况

**1. 一键更新要"无缝"，但宿主机和适配接口的工单是按"重启就断"写的（高，已补评论 #18、#25，已开工单 #110、#111）**

2026-11-14 用户要求更新时正在运行的沙箱和回合不中断。照现在的工单写出来的会是：

- dsh 是守护进程直接起的子进程。守护进程一重启，dsh 跟着退出，回合就断了；
- Git 代理、模型网关的转发、出站代理都在守护进程里。它一重启，正在进行的推送和模型流全断；
- 主站换进程时，会话的新事件通知只在进程内传（`Topic`），新旧两个进程并存的那一会儿，连在旧进程上的浏览器收不到新事件；定期任务会跑两份。

这些要在写宿主机和适配接口的时候就按能交接来设计，后补很贵。已经写进评论：dsh 由沙箱里常驻的**运行器**托管，守护进程断了能重连；守护进程能把监听的端口交给新进程，旧的把手上的做完再退。主站那边的改动在 #110。

**2. 等管理员回答时，5 分钟就休眠、题目作废（中，要用户定，见第六节第 2 条）**

规格 #13、#32、#42：Agent 出了选择题或请求批准，会话算闲置，5 分钟后照常休眠，题目标为"已失效"，回合结束；管理员之后的回答作为新消息发出、带上原题。管理员多半是在手机上收到通知才点进来，超过 5 分钟是常事。结果是多数选择题都会作废，Agent 要重开一个回合、重新读一遍上下文，批准到一半的操作也接不上。

**3. 用 Git LFS 的仓库用不了（中，要用户定，见第六节第 4 条）**

Git 代理的规则里，`github.com` 上除了 git 的推拉，只放行只读的请求。LFS 取大文件要先 POST 一个批量接口，会被拒。结果是克隆下来的大文件全是指针，推送带 LFS 的提交也会失败。

**4. 主站没有反向代理时，任何人都能让管理员登不进去（中，已开工单 #94）**

2026-11-11 的复查说过"没有反向代理时频率限制能被绕过"。还有反过来的一面：这时所有人的来源都是同一个（`unknown`），而限制是"同一个来源一小时输错 10 次，之后正确的密码也要等"。所以任何人每小时故意输错 10 次，管理员自己也登不进去。#94 里加了"前面有几层反向代理"的设置，0 层时用连接的来源地址。

**5. 路径方式的预览会被 Service Worker 用首页顶掉（中，已补评论 #39）**

主站是 PWA，Service Worker 只把 `/api/` 排除在"用缓存的首页代替"之外。没配预览域名时，预览放在主站域名下的路径里，页面请求会被换成首页。预览的路径要放在 `/api/` 下面，或者加进排除的清单。发给管理员的 HTML 文件预览同理。

**6. 提交和 PR 里的会话链接会把自己部署的主站地址写进公开仓库（中，要用户定，见第六节第 3 条）**

**7. 每收到一条文字增量就查一次库（低，已补评论 #31）**

`Sessions.#forwardLive` 为了丢掉晚到的增量，每条都查一次回合还在不在跑。接上真宿主机以后一个会话每秒几十条。

**8. 没有部署用的任何东西，主站是用 `tsx` 直接跑源码的（中，已开工单 #94）**

`apps/site` 的 `start` 是 `tsx src/server/main.ts`，`pnpm build` 只构建前端；仓库里没有镜像、没有安装脚本。部署向导和一键更新两份规格都得先有"发布包是什么"，定在了 #94 和 #108：主站用 Docker Compose 跑，宿主机守护进程用 systemd 跑，每个版本发主站镜像、守护进程的压缩包和通用镜像。

**9. 2026-11-14 定了的几件事没有工单（中，已开工单）**

用量上限（#115）、两步验证和通行密钥（#100）、中国大陆的网络和内网部署（#96）、备份恢复和密钥轮换（#99）。

**10. dsh 上游已经出到 0.2.2-rc.3（低，见 #17）**

调研和规格都是按 rc.1 写的。2026-11-15 查 npm：`latest` 还是 rc.1，`next` 是 rc.3。锁哪个版本、rc.1 之后 SDK 协议变了什么，在 #17 里核对。

**11. "依赖的许可证和 AGPL-3.0 兼容就行"这条规矩太宽（中，已改 `CLAUDE.md`）**

ADR 0009 和 `CLAUDE.md` 写的是"以后加的代码和依赖，许可证都要和 AGPL-3.0 兼容"。GPL、AGPL 的第三方库也算兼容。但 `CONTRIBUTING.md` 要求贡献者同意作者以其他许可证再授权：整个程序里只要有一段作者没法另行授权的代码（别人的 GPL、AGPL 库），这条声明对整个程序就落空了。`licenses.ts` 的类型里现在只有 MIT、Apache-2.0、OFL-1.1 三种，实际没有越界，只是规矩没写明。`CLAUDE.md` 的开发命令里补了一条：主站和宿主机的运行时依赖只用宽松的许可证；DSH Go（AGPL-3.0）的代码只进安卓 App。新规格里凡是写"许可证要和 AGPL-3.0 兼容"的地方，都按这一条理解。

**12. Agent 模式里的创造模式，在 SDK 下能不能做全还不知道（中，已开工单 #128）**

dsh 网页版的创造模式有一个查看运行时的工具，依赖网页版才有的部件。#128 先验证，再定怎么做。

## 五、安全

2026-11-11 排查过的不重复。新看到的：

**1. 抓取接口是一条绕过网络策略的路（高，要用户定，见第六节第 1 条；先按保守的做法写进了 #26 的评论）**

环境的网络策略有"不开放"和"默认清单"两档，意思是沙箱里的东西出不去、或者只能去清单里的地方。但 Agent 的网页抓取工具走的是模型网关的抓取接口：主站替它去取任意网址。于是不管哪一档，Agent 都能把读到的内容拼进一个网址里取一下，送到外面去。提示词注入最想要的就是这条路。

**2. 没有反向代理时的登录限制**，见第四节第 4 条。

**3. 会话链接暴露部署地址**，见第六节第 3 条。

**4. 插件装进每个会话（中，写进了 #133）**

插件中心定了打开、开源版可以自己加插件市场。插件的代码跑在沙箱里的 dsh 进程中，碰不到宿主机和主站上的凭据，但能读到会话的对话、能以 Agent 的权限操作。#133 里要求：安装前写明来源和这一点；只有管理员能往全站的清单里加，Agent 的工具加不了；git 来源固定到提交；主站取索引时不连内网。

**5. 一键更新不能让主站拿到整台机器（高，写进了 #110）**

最省事的做法是把 Docker 的接口挂给主站的容器，让它自己换自己。那等于给了一个网页应用整台机器的 root，而这个应用只隔着一个密码。#110 定的是：主站只能往一个目录里写"请更新到版本 X"，机器上另一个更新程序自己去核对版本、下载、校验，不执行请求里的任何内容。

**6. 看过、没有新问题的**

PR #61–#87 新加的接口（设置、昵称、置顶、已读未读、附件的入口）都先查登录、按管理员的 ID 过滤；设置的值按固定的形状校验；CI 只在 GitHub 托管的环境里跑，fork 来的 PR 拿不到密钥。

## 六、要用户定的

每条先写 Claude Code 网页版怎么做，再给建议。

**1. 网页抓取要不要受环境的网络策略约束**

- Claude Code 网页版：联网搜索和抓取是 Anthropic 服务端的工具，不经过沙箱的出站，文档里网络策略管的是沙箱自己发出的连接。这一点没有查到明文，是按它的工具说明推断的。
- 建议：折中。"不开放"档拒绝抓取，这一档的意思就是出不去；"默认清单""自定义"两档放行抓取，但每次抓取都记进出站访问记录，在会话里看得到，并在环境的说明里写明"抓取不受清单限制"；"完全开放"不限。全按清单卡的话，Agent 查个文档都要先改环境，太不好用。
- 定之前，#26 先按最保守的写（两档都按清单判断）。

**2. 等管理员回答时要不要照常 5 分钟休眠**

- Claude Code 网页版：等回答时题目不会因为闲置而失效，回来还能接着答。
- 建议：停在选择题、批准、计划卡片上的会话不按 5 分钟休眠，单独一个时长，默认 24 小时，设置里可改；宿主机资源不够、要挑会话提前休眠时，这类排在最后。开源版的宿主机是管理员自己的，多留一会儿只占他自己的内存。

**3. 提交和 PR 里的会话链接默认加不加**

- Claude Code 网页版：加。它的链接指向 claude.ai，不暴露用户自己的东西。
- SeekCloud 的链接指向管理员自己部署的主站。现在的规格（#57）是跟着 AI 标识的开关走，默认开：公开仓库的提交历史里就会留下一批 SeekCloud 部署的地址，别人搜得到。
- 建议：会话链接单独一个开关，默认关；AI 标识的署名和提交尾注照旧默认开。

**4. 要不要支持 Git LFS**

- Claude Code 网页版：没有查到明文。

**14. 侧栏的分组和拖动排序**（`CLAUDE.md` 里留着要定细节的）

- Claude 的 App：会话的"⋯"菜单里有置顶、标为未读、移到分组；长按会话可以拖动。
- 建议：
  - 分组在"⋯ → 移到分组"里新建或选择；侧栏里每个分组是一个可以折叠的标题，置顶的一组永远在最上面，"最近"在最下面；
  - 分组里的会话可以拖动排序，顺序是手动的；"最近"那一组仍然按最近有动静排，不能拖；把会话从"最近"拖进一个分组，就等于移到那个分组；
  - 分组可以改名、删除；删除分组时里面的会话回到"最近"；空的分组留着，直到手动删；
  - 归档的会话离开分组。
