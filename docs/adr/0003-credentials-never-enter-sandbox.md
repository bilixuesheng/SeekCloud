# 凭据一律不进沙箱：模型网关和 Git 代理

用户可以控制沙箱里的 shell，所以放进沙箱的任何凭据都等于交给了用户。DeepSeek 开放平台协议 §2.2 禁止共享 API Key、禁止把它暴露在客户端。因此沙箱里只放一个**会话临时令牌**，所有对外的凭据都留在沙箱之外：

- **模型网关**：沙箱里的 Agent 只能通过它调用模型。网关负责换上真正的 DeepSeek Key，附上每个用户的 `user_id`。
- **Git 代理**：沙箱访问 GitHub 的唯一通道。规则完全照搬 Claude Code 的 GitHub 代理：
  - 沙箱里的 git 和 `gh` 只拿到限定本会话的凭据（`gh` 的 `GH_TOKEN` 是占位符），代理校验后换成用户真正的 GitHub 令牌；
  - 只能访问本会话挂载的仓库，公开仓库也要先挂载；
  - 禁用 GraphQL 接口，因为没法按仓库限制它的访问范围；
  - 拒绝删除分支和推送分支以外的东西（比如标签）；
  - **不限制推送到哪个分支，也允许强推**。主分支要靠用户自己在 GitHub 上设置分支保护规则。

  我们考虑过默认禁止推送 main，但为了和 Claude 保持一致，没有这么做。
- **提交签名**：提交的作者是 SeekCloud 专用的 GitHub 账号，每个提交都用它的 SSH 密钥签名，GitHub 上显示 Verified。签名密钥放在宿主机上，沙箱里的 git 通过一个签名助手请宿主机代签。

GitHub 上的身份也照搬 Claude：评论、开 PR、review 用用户本人的 GitHub 账号，每条带"由 SeekCloud 生成（AI）"的署名（默认加上，管理员可以在设置里关掉）；提交的作者是 SeekCloud 账号，就像 Claude 的提交作者是 claude 账号。

这和 Claude Code 网页版的做法一致：它的 GitHub 凭据和签名密钥都只放在服务端。这样做的另一个好处是，权限的规则只需要在一个地方执行，无论沙箱里跑的是哪个 Agent 都一样。

## 部署位置

- **模型网关放在主站**。DeepSeek Key 只存在主站一个地方。因为每次模型请求都带着完整上下文，主站必须选不限流量的机器。
- **Git 代理放在每台沙箱宿主机上**，在沙箱之外运行。拉代码、推代码的流量就留在宿主机本地。
  - GitHub App 的私钥和用户的刷新令牌只放在主站。
  - 会话运行期间，主站把用户的访问令牌（GitHub 规定最长 8 小时）通过协议下发给宿主机，只放在内存里；快过期时主站刷新后再下发。
  - 用户的访问令牌没法限定到某几个仓库，所以仓库范围完全靠 Git 代理检查。

## Considered Options

- **GitHub App 的安装令牌**（能限定到本会话的仓库，1 小时有效）：原先的方案。它能在 GitHub 那一侧限定范围，但 Agent 的评论和 PR 会显示成 SeekCloud App，和 Claude 不一致。2026-10-31 用户要求权限和 Claude 完全一样，改成了现在的做法。
- **提交以用户本人身份、不签名**：grilling 时的原方案。2026-10-31 改为照搬 Claude。

## Consequences

- 无论网络策略是哪一档，包括"不开放"，模型网关和 Git 代理都必须能连通。
- 网关不对沙箱以外的调用方开放，否则就成了 DeepSeek 条款禁止的"转售 API"。
- 宿主机被攻破时，能拿到的是正在运行的会话的用户访问令牌：最长 8 小时有效，范围是这个用户本人能访问、而且装了 SeekCloud App 的仓库。比原方案的范围大，换来的是和 Claude 一致的身份。
- 要注册一个 SeekCloud 专用的 GitHub 账号，并把签名公钥加到它上面。
- Agent 能改仓库里的工作流文件（GitHub App 有 workflows 写权限），工作流跑起来能做代理不放行的事，比如建标签、删分支。这一点和 Claude 一样，靠用户自己的分支保护和代码审查兜底。代理只是不让 Agent 直接做这些事。
