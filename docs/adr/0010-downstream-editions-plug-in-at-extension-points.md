# 主干不分叉：下游版本只在扩展点上接入

本仓库是 SeekCloud 付费版的开源、自部署主干版本。主干只有一个管理员（ADR 0008），不计费，也不替别人管账户。下游版本要的东西和主干不一样，但会话、宿主机、沙箱、模型网关、平台工具这些只应该写一遍。所以要定下来：下游怎么接进主干，主干为此要守哪些规矩。

**下游版本**指在主干之上做出来的另一个发行版，也包括任何人按 AGPL-3.0 改造出来的版本。

这件事要在宿主机和模型网关那批工单动工之前定：这两块正是下游改动最多的地方，定晚了两边就各写各的。

## 决定

### 1. 主干是库，入口只做组装

- 主站的服务端是 `createApp(deps)`：所有可以替换的东西都从 `deps` 进来。`apps/site/src/server/main.ts` 只做一件事：读环境变量，挑主干的那一份实现，组装起来。
- 浏览器端同理：页面、设置分类、文案都登记在注册表里，`apps/site/src/client/main.tsx` 登记主干的那些。
- 下游有自己的入口文件。它把主干当作依赖引用（git 子模块加 pnpm workspace），组装时换掉其中几样、再加上自己的路由和页面。**下游不改主干的文件**，所以跟主干同步时没有合并冲突，只有接口变了时的类型错误和测试失败。

### 2. 扩展点：一个接口，主干里只有一份实现

**扩展点**是 `deps` 里的一个接口。主干里有且只有一份实现，就是单管理员、不计费的那一份，而且主干自己在用它。

- 主干里不放下游的实现，不放"版本开关"，不写"如果是某个版本就……"的分支。主干的代码读起来就是一个单管理员的产品。
- 一个扩展点如果主干自己用不上（主干的实现只是原样放行），就不加。下游要在这种地方做事，用下面第 3 条的通用办法。
- 扩展点在它所在的那块代码第一次写的时候就按这里的形状写，不另做一轮重构。

| 扩展点 | 它回答的问题 | 主干的实现 | 在哪张工单里做 |
|---|---|---|---|
| 身份来源 | 这个请求是谁发的；登录、退出这组路由 | 管理员密码登录（`auth/admin-identity.ts`） | #89 |
| 设置的读写规则 | 一项设置的默认值是什么、现在能不能改 | 默认值写在主干里，管理员都能改（`settings.ts` 的 `adminSettings`） | #89 |
| 模型调用的准入和记录 | 这次模型调用放不放行；用了多少、为了什么用的 | 记用量；可选的用量上限 | #26、多提供方的规格 |
| 提供方路由 | 这个模型的请求依次试哪几个提供方；发出去之前怎么改写请求 | 只有管理员选的那一个，所以不会自动换提供方；剥掉 dsh 夹带的字段，换上 key，不附带使用者标识 | #26、多提供方的规格 |
| 排队策略 | 资源空出来时先启动哪个会话；一个会话现在能不能启动 | 先到先得，只看宿主机资源 | #45 |
| 报错的呈现 | 一个内部错误，给浏览器看哪些内容 | 类别、状态码、参考号，加上上游的原始报错（ADR 0007 的修订） | #26 |
| 版本来源 | 一键更新从哪里读版本、取发布包 | 本仓库在 GitHub 上发的版本 | 一键更新的规格 |
| 通知渠道 | 一条通知经哪些途径送出去 | SMTP 邮件、PWA 推送、几种机器人、通用 Webhook | 多渠道通知的规格 |
| 插件市场的来源 | 插件市场里列哪些索引源 | 管理员自己维护的列表 | 插件市场的规格 |

平台自己发起的模型调用（起标题、判断是不是在等管理员输入、安全审查、看图）和 Agent 的调用走同一个"准入和记录"，记录里带上用途。

### 3. 不够用时的通用办法

- **路由前后的中间件**：下游在组装时可以给主干的路由套中间件（比如在消息进会话之前检查一遍，或者给上传的接口加大小上限）。主干不为此留专门的钩子。
- **包一层**：扩展点的实现可以包住主干的实现再加东西（比如包住提供方，在响应流经过时处理）。
- 两种办法都做不到、非改主干不可时，先在主干提一个扩展点，按第 2 条的规矩评估，不在下游打补丁。

### 4. 浏览器端的注册表

- **路由表**：路径到页面。主干登记首页、会话页、设置、开源声明。
- **设置分类**：设置窗口左边的每一类是一项登记。
- **插槽**：页面上几个有名字的位置（侧栏底部、输入框下方、会话顶部的提示条、首页问候语下方），登记进来的组件按顺序显示。只在主干自己也往里放东西的位置上开插槽。
- **文案目录**：界面文案按键存放，中英各一份（见英文界面的规格）。下游可以再叠一层，盖掉其中几条。

### 5. 数据的规矩

- 属于管理员的每一行数据都带 `user_id`，每一次读写都按身份来源给出的 ID 过滤。除了 `auth/admin.ts`，任何地方不许用"取库里唯一的那个管理员"的写法。
- 下游的表放在下游自己的迁移目录里，用外键指向主干的表，不改主干的表。两边的迁移各记各的。
- 协议包里的固定列表（错误类别、回合结束的原因、状态的附加说明）下游不能加值。主干要给出够用的通用值，比如"因用量限制暂停"。
- 沙箱宿主机、主站和宿主机之间的协议、dsh 修改版不分版本。下游的差别都放在主站的扩展点里。

### 6. 守住这些规矩的测试

- **契约测试**：每个扩展点一套，从主干导出。主干的实现要过，下游的实现也跑同一套。
- **隔离测试**：测试里用一个假的身份来源放进第二个身份，检查会话、环境、导出、设置的接口互相看不到对方的数据。产品里没有第二个账户，这只是测试替身，用来守住第 5 条的第一项。ADR 0008 说过这些检查"没有测试再覆盖"，这里补上。
- **最小下游**：测试目录里放一个最小的样例，把每个扩展点各换成一个假实现，再把主站起起来。它保证组装的入口一直能用；有人把某个扩展点写死了，这个测试会失败。

## Considered Options

- **下游维护一个分叉，把自己的改动一直变基到主干上**：没有采用。主干每动一次相关的文件就要解一次冲突，一个人维护不过来，也没有测试能提前发现。
- **在主干里用开关区分版本**：没有采用。主干里会留着自己用不上的代码和分支，读的人分不清哪些是给谁的；ADR 0008 也已经定了主干不放多账户的代码。
- **运行时加载的插件系统**：没有采用。组装发生在构建时就够了，运行时加载还要另管版本兼容和加载顺序。
- **下游在主干前面另起一层服务，每个使用者配一套主干**：没有采用。每多一个使用者多一个进程和一个库，宿主机也没法统一调度。

## Consequences

- 扩展点的签名是对下游的承诺。改签名要在发布说明里单列"扩展点变更"。
- 主干多了一层间接：身份、设置、网关、调度都经过接口。每个扩展点主干自己都在用，这层间接同时也是主干自己的测试缝。
- 下游把自己的模块和主干跑在同一个进程里，分发或对外提供服务时按 AGPL-3.0 和署名附加条款办（ADR 0009）。
- ADR 0008 不变：主干仍然只有一个管理员，以后也不加多账户。
