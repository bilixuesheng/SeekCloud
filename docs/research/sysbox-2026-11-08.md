# Sysbox 调研：WSL2 上能不能跑，云端会话的机器上为什么装不了（2026-11-08）

两部分：

- 第一部分：Sysbox 能不能在 Windows 的 WSL2 里运行（只读调研，日期按洛杉矶时间）。决定 SeekCloud 的沙箱宿主机能不能装在 Windows 上。
- 第二部分：在 Claude Code 云端会话的机器上试装 Sysbox CE 0.7.1，看它能不能当沙箱宿主机的测试环境。

标注说明（第一部分用）：
- **[官方]**：Sysbox 仓库的文档、代码，Docker、Microsoft、gVisor 的官方文档或发布说明。
- **[个案]**：issue 里个别用户或维护者的实测记录，不代表官方支持承诺。
- **[推断]**：根据上面两类资料推出来的，没有找到直接说法。

## 结论

WSL2：

1. Sysbox 官方文档的支持列表里**没有 WSL2，也没有 Windows**，整个 docs 目录搜不到 "WSL"。[官方]
2. 但**实际能跑**：Sysbox 维护者 ctalledo 2024-04 在 WSL2 的 Ubuntu 22.04 上跑通 sysbox-ce v0.6.4；安装包从 2024-01 起会识别 WSL2，跳过两步只适用于 Ubuntu 的安装步骤；Docker 官方的 Enhanced Container Isolation（ECI，底层就是 Sysbox）明确支持 WSL2 后端。[个案 + 官方]
3. 现在 WSL 自带的内核（稳定版 WSL 3.0.3 是 6.18.54.1，WSL 2.6 起是 6.6）已经高于 Sysbox 要求的 5.19，不需要 shiftfs，idmapped mounts 也满足。[官方 + 推断]
4. 必须满足几个前提，否则会失败：在 WSL 发行版里自己装 Docker Engine，**不能用 Docker Desktop 的引擎**；`.wslconfig` **不能开 `networkingMode=mirrored`**（seccomp 冲突，微软未修）；开 systemd；内核要 5.19 以上（老内核有已知的文件损坏 bug）。[个案 + 官方]
5. 适合 SeekCloud 的方案：WSL2 + 自装 Docker Engine + Sysbox CE（NAT 网络，不开 mirrored），作为"非官方支持但实测可用"的路线；要官方支持或更强的隔离，就用 Hyper-V 虚拟机装 Ubuntu 24.04 + Sysbox（只有 Windows 专业版、企业版能用）。gVisor 在 WSL2 上有人在用，但官方没有说明支持。[推断]

云端会话的机器：

6. **装不了**。官方 sysbox-runc 起容器时要把容器 init 进程的 `oom_score_adj` 调到 -999，需要 `CAP_SYS_RESOURCE`；云端会话的机器是 Firecracker 虚拟机，所有进程的 bounding set 里都没有这个能力，root 也拿不回来，所以起不了任何容器。测试机要用一台普通的 Ubuntu 24.04 服务器。

## 一、WSL2

### 1. Sysbox 官方支持的发行版和内核要求

来源：仓库 `docs/distro-compat.md`、`docs/user-guide/design.md`、`docs/user-guide/install-package.md`（master 分支 `b77c3716`，2026-10-20 提交）。最新发布是 v0.7.1（CHANGELOG 记为 2026-07-28）。

- **支持的发行版** [官方]：Ubuntu 24.04（内核 6.8+）、22.04（5.15+）、20.04（5.4+）、18.04（5.3+）；Debian 11、10（5.5+）；可以从源码构建的有 Fedora、Rocky、Alma、CentOS Stream、Amazon Linux（5.12+）；Flatcar 和 RHEL 只限已停止的 Sysbox-EE。安装包只出 Ubuntu 和 Debian 的 `.deb`。
  > "These are the Linux distros we officially support (and test with). However, we expect Sysbox to work fine on other Linux distros too, particularly with kernel >= 5.12."
- **shiftfs 要求** [官方]：

  | 内核版本 | 需不需要 shiftfs |
  | --- | --- |
  | < 5.12 | 需要 |
  | 5.12 到 5.18 | 不需要（但推荐装） |
  | >= 5.19 | 不需要 |

  shiftfs 是 Ubuntu 内核才带的模块，Debian 和 Flatcar 可以手动装，其他发行版没有。
- **ID-mapped mounts** [官方]：Sysbox 从 v0.5.0 起用内核 5.12+ 的 ID-mapped mounts 做用户 ID 映射；"as of kernel 5.19+, ID-mapped mounts provide an almost full replacement for shiftfs"。
- **其他宿主机要求** [官方]：宿主机的进程管理器必须是 systemd；推荐至少 4 个 CPU、4 GB 内存；Sysbox 必须以 root 运行。
- **Sysbox 会拦截系统调用** [官方]：对 `mount`、`umount2` 等少数调用做拦截（security.md "System Call Interception"）。sysbox-runc 源码里用的是 seccomp notify（`libsysbox/syscont/syscalls.go` 的 `SeccompNotif`）。这一点和下面 WSL mirrored 网络的冲突有关。

### 2. WSL2 默认内核满不满足

- **当前默认内核版本** [官方]：
  - microsoft/WSL 的发布页：最新稳定版 **3.0.3**（标为 Latest，10 月 9 日发布，页面上没有年份，按前后版本推断是 2026 年）的说明是 "Update Microsoft.WSL.Kernel to 6.18.54.1"；预发布版 3.0.5（11 月 3 日）是 6.18.58.1。
  - Docker 的 ECI 文档："WSL 2.6+ includes kernel version 6.6"。
  - microsoft/WSL2-Linux-Kernel 仓库现在有两条线，`linux-msft-wsl-6.6.y` 和 `linux-msft-wsl-6.18.y`，最新 tag 分别是 6.6.123.2 和 6.18.58.1。
- **内核配置**：我直接看了 `linux-msft-wsl-6.6.123.2` 和 `linux-msft-wsl-6.18.58.1` 两个 tag 的 `arch/x86/configs/config-wsl`。下面这些在两个版本里都开着 [官方]：`CONFIG_USER_NS`、`CONFIG_FUSE_FS`（sysbox-fs 要用）、`CONFIG_OVERLAY_FS`、`CONFIG_SECCOMP_FILTER`、`CONFIG_CGROUPS`、`CONFIG_MEMCG`、`CONFIG_CGROUP_BPF`、`CONFIG_VETH`、`CONFIG_BINFMT_MISC`、`CONFIG_IA32_EMULATION`、`CONFIG_SECURITY_APPARMOR`。另外 `CONFIG_KVM_INTEL`、`CONFIG_KVM_AMD` 是模块（=m），说明支持嵌套虚拟化。
- **能不能满足 Sysbox** [推断]：
  - 6.6 和 6.18 都高于 5.19，不需要 shiftfs，ID-mapped mounts 也够用（包括 overlayfs 叠在 ID-mapped mounts 上）。
  - WSL 内核没有 shiftfs，也装不了这种树外模块（见 issue #868 维护者的说法）。
  - 如果是 2.6 以前的 WSL（内核 5.15），会碰到下面 #868 那个 bug。
- **cgroup** [官方]：`wsl.conf` 的 `[automount] cgroups` 默认 `v2`；`.wslconfig` 有 `isolateDistroCgroup`，默认 true。
- **systemd** [官方]：`wsl.conf` 里写 `[boot] systemd=true` 打开（需要 WSL 0.67.6+）；用 `wsl --install` 装的 Ubuntu 默认就开着。wsl-config 页面写着 "The Boot setting is only available on Windows 11 and Server 2022"，但 systemd 页面只要求 WSL 版本，两页说法不一致。Windows 10 上能不能开，要实测。

### 3. 官方对 WSL2、Docker Desktop 的态度

- **Sysbox CE 文档** [官方]：没写支持，也没写不支持；docs 目录里完全没提 WSL 或 Windows。README 提到 Docker Desktop 只有一处：Sysbox-EE 已经并进了 Docker Desktop 的 Hardened Desktop。
- **Sysbox 的安装包已经认 WSL2** [官方]：sysbox-pkgr PR [#121](https://github.com/nestybox/sysbox-pkgr/pull/121)，"Add WSL2 detector"，作者 arukiidou，2024-01-13 由 ctalledo 合并，并关联了 issue #32。现在的 `deb/sysbox-ce/sysbox-ce.postinst` 用 `uname -r` 里有没有 `microsoft` 判断是不是 WSL2；是的话，跳过 `enable_unprivileged_userns`（WSL 内核没有 `/proc/sys/kernel/unprivileged_userns_clone`）和 `check_kernel_headers`。
- **Sysbox 的 issue #32 已关闭** [官方]：标题 "Add support for running Sysbox on Windows (via WSL2)"，里程碑 v0.6，关联上面的 PR #121。页面上没显示关闭原因。
- **Docker Desktop**：
  - 普通 Docker Desktop **不能**用 Sysbox CE [个案，维护者说的]：2025-06-18 ctalledo 在 #32 里说："you can't make Docker Desktop use Sysbox otherwise"，意思是 Sysbox 只能通过 Docker Business 的 Hardened Desktop 功能在 Docker Desktop 里用。
  - ECI（底层是 Sysbox）**支持 WSL2 后端** [官方]：要求 "WSL version 2.6 or later because ECI depends on a Linux kernel version of at least 6.3.0"；开了 ECI 后，容器的运行时显示为 `sysbox-runc`。前提是 "A Docker Business subscription"。
  - Docker 自己写了 ECI 在 WSL2 上的局限 [官方]："All WSL 2 distributions share the same Linux kernel instance"；"Other WSL distributions can modify kernel settings that affect Docker Desktop's security"；"On WSL, Docker Desktop can't guarantee the integrity of kernel level configs"；"WSL 2 ... provides reduced security isolation"；用户可以 `wsl -d docker-desktop` 直接拿到 root 绕过。
  - Docker Desktop 下用自定义 WSL 内核 [官方]："not officially supported"。

### 5. 在 Windows 上跑带隔离的 Linux 沙箱，有哪些替代方案

| 方案 | 隔离边界 | 支持情况 | 前提和代价 |
| --- | --- | --- | --- |
| **A. WSL2 + 自装 Docker Engine + Sysbox CE** | 容器（user namespace，加上 procfs/sysfs 虚拟化）。所有 WSL 发行版共用一个内核 | Sysbox 文档没写；安装包认 WSL2；维护者实测可用 [官方 + 个案] | WSL 2.6+（内核 6.6+）；systemd=true；**不开 mirrored**；不用 Docker Desktop 的引擎；Ubuntu 22.04/24.04 发行版 |
| **B. Docker Desktop + ECI** | 同 A | Docker 官方支持 WSL2 后端 [官方] | 需要 Docker Business 订阅；只能由 ECI 自动套用，不能自己选 `sysbox-runc`；Docker 自己说 WSL 后端的隔离比 Hyper-V 后端弱。开源自托管不适用 [推断] |
| **C. Hyper-V 虚拟机 + Ubuntu 24.04 + Sysbox** | 硬件虚拟化（VM），里面再套 Sysbox 容器 | Ubuntu 24.04 在 Sysbox 的官方支持列表里 [官方]；#868 里有人在 Hyper-V 上的 Vagrant Ubuntu 虚拟机里跑过 Sysbox [个案] | Hyper-V 只有 Windows 10/11 专业版、企业版能装，家庭版不行 [官方]；要自己管虚拟机的生命周期和网络，一键安装更难做 [推断] |
| **D. WSL2 + 自定义内核** | 同 A | `.wslconfig` 支持 `kernel=`、`kernelModules=` [官方] | 现在默认内核已经够用，Sysbox 不需要自定义内核 [推断]；企业可以用 Intune 禁止自定义内核 [官方]；Docker Desktop 不支持自定义内核 [官方]。只有需要编进额外的内核功能时才值得 |
| **E. WSL2 + 自装 Docker Engine + gVisor（runsc）** | 用户态内核拦截系统调用 | gVisor 文档只写 "requires Linux 5.6+"，没提 WSL [官方]；有人在 WSL2 内核 6.6.87.2 上用 runsc release-20260907.0 正常运行（报的是别的时钟 bug）[个案，[gvisor#17066](https://github.com/google/gvisor/issues/17066)]；cgroup v1 的 WSL2 上 kind 里的 runsc 起不来 [个案，[choregos#905](https://github.com/VargaFoundation/choregos/issues/905)] | 默认的 systrap 平台用的是 `SECCOMP_RET_TRAP`，不是 notify listener，所以 mirrored 模式的 EBUSY 问题按理不影响它 [推断，未实测]；Docker Desktop 没有正式加 runsc 的办法 [个案，[desktop-feedback#364](https://github.com/docker/desktop-feedback/issues/364) 还开着]。另外，在 gVisor 里跑 systemd、Docker in Docker 不如 Sysbox 方便 [推断] |
| **F. WSL2 嵌套虚拟化 + KVM（Kata、Firecracker、gVisor 的 KVM 平台）** | 每个沙箱一个轻量虚拟机 | `nestedVirtualization` 默认 true，但只限 Windows 11 [官方]；WSL 内核把 KVM 编成了模块 [官方]；gVisor 文档说嵌套虚拟机里 systrap 往往比 KVM 平台更快 [官方] | 没找到 Kata、Firecracker 在 WSL2 上的官方说明，没有查证 [推断] |
| **G. WSL 容器（`wslc.exe`）** | 每个会话一个 WSL 虚拟机 | WSL 2.9.3+ 自带的新功能，有命令行和 NuGet API [官方] | 隔离模型、能不能跑 Docker in Docker、是不是每个容器一个虚拟机，这次都没查，要另外调研 |

#### 加固和边界情况 [推断]

- **空闲自动关机**：WSL 默认 `instanceIdleTimeout`（15 秒，发行版空闲后关闭）和 `vmIdleTimeout`（60 秒，只限 Windows 11）。宿主机守护进程要常驻，需要设成 -1 或者保证有前台进程，否则沙箱可能被一起关掉。上面的默认值是官方的；会不会真的关掉沙箱，要实测。
- **Windows 文件和程序互通**：WSL 默认把 `C:` 挂到 `/mnt/c`，也能直接运行 Windows 程序（interop）。Sysbox 容器即使逃逸出来也只是没有特权的用户，但宿主机的那个发行版建议关掉 `[automount] enabled` 和 `[interop] enabled`，减小逃逸后能碰到的东西。
- **共用内核**：同一台 Windows 上的其他 WSL 发行版和 SeekCloud 的宿主机发行版共用一个内核，能改内核设置（Docker 官方也这么说）。所以最好不要和用户的日常发行版混用，或者明确告诉用户这一点。
- **mirrored 网络**：Windows 11 22H2+ 才有，默认是 NAT。用户如果自己开了 mirrored，Sysbox 会直接失败。安装向导要检测 `.wslconfig` 并提示。
- **Windows 10**：嵌套虚拟化、mirrored 网络只限 Windows 11；systemd 在 Windows 10 上能不能用，文档说法不一致（见第 2 节）。要不要支持 Windows 10，得实测后再定。

## 二、在云端会话的机器上试装

目的：看 Claude Code 云端会话的机器能不能当沙箱宿主机的测试环境。

### 机器概况

- Ubuntu 24.04.5 LTS，内核 `6.18.44-fc-v310`（Firecracker 虚拟机，PID 1 是 `process_api`，不是 systemd），root。
- Docker 29.9.2、containerd 2.4.2、runc 1.5.2 已装；`/etc/docker/daemon.json` 原本不存在。

### 第 1 步：前提检查

| 项目 | 结果 | 说明 |
| --- | --- | --- |
| 内核版本 | 6.18.44 | Sysbox 要求 ≥5.12（idmapped mounts）、≥5.19（overlayfs 上的 idmapping）；版本够 |
| 内核模块 | `# CONFIG_MODULES is not set`，cmdline 带 `nomodule` | 不能加载任何模块，`modprobe`/`lsmod` 也没装 |
| shiftfs | 没有 | `/proc/filesystems` 里没有 shiftfs，也不能装模块 |
| idmapped mounts（ext4 bind） | 能用 | `mount --bind -o X-mount.idmap=b:0:100000:65536` 成功，文件显示成 100000:100000（只给 `u:` 不给 `g:` 时失败） |
| idmapped mounts（叠在 overlay 挂载上） | 不行 | 对 overlay 挂载点再做 idmapped bind：`failed to attach idmapping` |
| cgroup | 混合模式（v1 + v2） | `/sys/fs/cgroup` 是 tmpfs，下面挂 v1 的 cpu、cpuacct、cpuset、memory、devices、freezer、blkio、pids、name=systemd；cgroup2 挂在 `/sys/fs/cgroup/unified`（没有控制器） |
| `/proc/sys/kernel/unprivileged_userns_clone` | 文件不存在 | 这是 Debian/Ubuntu 补丁才有的开关，上游内核没有，等于不限制；`user.max_user_namespaces=64267`，`unshare -U -r id` 成功 |
| systemd | 不可用 | PID 1 是 `process_api`，`/run/systemd/system` 不存在（`systemctl` 二进制在，但没用） |
| AppArmor | 内核没编进（`# CONFIG_SECURITY_APPARMOR is not set`） | Sysbox 不依赖 AppArmor |
| 其他 | `CONFIG_USER_NS`、`CONFIG_OVERLAY_FS`、`CONFIG_FUSE_FS`（sysbox-fs 要用）、`CONFIG_SECCOMP`、veth、bridge、iptables/nftables NAT 都编进了内核 | |

初步判断：内核新、idmapped mounts 能用、FUSE 在，Sysbox 有希望跑起来；缺 shiftfs 和 systemd，要手动起守护进程。

### 第 2 步：下载 sysbox-ce 0.7.1

- 最新版本：`git ls-remote --tags https://github.com/nestybox/sysbox` 最高是 `v0.7.1`（CHANGELOG：2026-07-28，加了 Ubuntu 24.04 + 内核 6.8+ + containerd 2.x 的支持）。
- 这台机器的网络代理拦了 GitHub releases 的页面和下载链接，GitHub API 也用不了。改用官方安装文档（`docs/user-guide/install-package.md`）里写的下载地址：
  `https://downloads.nestybox.com/sysbox/releases/v0.7.1/sysbox-ce_0.7.1-0.linux_amd64.deb`
  （307 跳到 `storage.googleapis.com/sysbox-releases/...`，Nestybox 自己的存储桶）。
- 14483412 字节：
  - sha256 `9d6d5484f980d0a17f86c492c1262015c2afb66280bdb97215b79fde6a0261c5`
  - md5 `1069e96936cd8afe6c98e63c515c0ccf`，和存储桶列表里的 ETag 一致（文档里只给了 0.7.0 的 sha256，没有 0.7.1 的，只能核对到这一步）
- 包内容：`/usr/bin/{sysbox-runc,sysbox-mgr,sysbox-fs}`、三个 systemd unit、`/lib/sysctl.d/99-sysbox-sysctl.conf`。依赖 jq、fuse、rsync、iptables、lsb-release。

#### 为什么不用 dpkg 装，改成手动装

读了包里的 preinst/postinst：

- postinst 会 `sysctl -w` 改 inotify 上限、`kernel.keys.maxkeys/maxbytes`、`kernel.pid_max=4194304`，还会往 `daemon.json` 里加 `bip: 172.20.0.1/16` 和 `default-address-pools`，并在有改动时 `systemctl restart docker`；
- 启动服务只靠 systemd（`deb-systemd-invoke`，没有 `/run/systemd/system` 时直接跳过）。

这台机器没有 systemd，试装时也不想改动机器上别的配置，所以只解包（`dpkg-deb -R`），手动做最少的几件事：拷三个二进制、加 `sysbox` 用户、建 `/var/lib/sysboxfs`、在 `daemon.json` 里只注册运行时。sysctl 没有动。

### 第 3 步：手动安装和注册运行时

#### 3a. 装二进制和依赖

- `apt-get install -y --no-install-recommends fuse3 rsync`：新装了 `fuse3`、`libfuse3-3`、`rsync`、`libpopt0`。原因：`sysbox-fs` 挂 FUSE 要 `fusermount3`/`fusermount`，`sysbox-mgr` 同步卷要 `rsync`；机器上原来都没有。
- `install -m 0755` 把 `sysbox-runc`、`sysbox-mgr`、`sysbox-fs` 拷到 `/usr/bin/`（和 .deb 的位置一致）。`sysbox-runc --version`：CE 0.7.1，commit `081856cc`，2026-07-31 构建。
- `useradd -s /bin/false sysbox`（和 postinst 一样）：`/etc/subuid` 和 `/etc/subgid` 自动加了一行 `sysbox:165536:65536`。
- `mkdir -p /var/lib/sysboxfs`（sysbox-fs 的挂载点）。
- 没有装 systemd unit、没有装 `/lib/sysctl.d/99-sysbox-sysctl.conf`、没有改任何 sysctl。

#### 3b. 手动启动 sysbox-mgr（碰到三个坑）

照 sysbox 仓库里 `scr/sysbox` 脚本的做法：`sysbox-mgr --log <文件> &`，再 `sysbox-fs --log <文件> &`，日志里出现 `Ready` 算起来了。

1. `level=fatal msg="failed to create sysbox-mgr: preflight check failed: modprobe is not installed on host."`
   → 预检要求有 `modprobe` 命令。`apt-get install -y --no-install-recommends kmod` 装上（内核本身不支持模块，`modprobe shiftfs` 照样失败，只是满足预检）。
2. `level=fatal msg="failed to create sysbox-mgr: shiftfs kernel module check failed: open /proc/modules: no such file or directory"`
   → 内核没开 `CONFIG_MODULES`，所以根本没有 `/proc/modules`；sysbox-libs 的 `KernelModSupported()` 打不开这个文件就直接报错。加 `--disable-shiftfs` 跳过 shiftfs 检查（本来也没有 shiftfs）。
3. `level=fatal msg="failed to create sysbox-mgr: binfmt_misc kernel module check failed: open /proc/modules: no such file or directory"`
   → 同一个原因。源码（`sysbox-mgr/mgr.go` 约 293 行）只在"系统容器模式"下检查 binfmt_misc，没有单独关掉的开关。
   → 绕法：全局用 `--syscont-mode=false` 启动 sysbox-mgr，再在每个容器上加环境变量 `SYSBOX_SYSCONT_MODE=TRUE` 打开系统容器模式（sysbox-runc 支持按容器覆盖，见 `sysbox-runc/libsysbox/syscont/spec.go` 约 1112 行）。代价：不会自动给容器挂 binfmt_misc（对测试没影响）。
   → **这是这台 Firecracker 虚拟机内核特有的问题**，正常的 Ubuntu 服务器内核有模块支持，不会碰到。

最终启动命令（两个都 `Ready ...`）：

```
nohup sysbox-mgr --disable-shiftfs --syscont-mode=false --log <日志目录>/sysbox-mgr.log > <日志目录>/sysbox-mgr.stdout 2>&1 &
nohup sysbox-fs --log <日志目录>/sysbox-fs.log > <日志目录>/sysbox-fs.stdout 2>&1 &
```

sysbox-mgr 日志的关键几行：

```
level=info msg="Use of shiftfs disabled."
level=info msg="ID-mapped mounts supported by kernel: yes"
level=info msg="Overlayfs on ID-mapped mounts supported by kernel: yes"
level=info msg="Operating in regular container mode."
level=info msg="Listening on /run/sysbox/sysmgr.sock"
level=info msg="Ready ..."
```

sysbox-fs：`FUSE dir = /var/lib/sysboxfs`、`Listening on /run/sysbox/sysfs.sock`、`Ready ...`。（sysbox-mgr 自己建了 `/var/lib/sysbox`、`/run/sysbox`。）

#### 3c. 注册运行时、重启 dockerd

- 新写的 `/etc/docker/daemon.json`（只注册运行时，没加 postinst 那些 `bip`、`default-address-pools`）：
  ```json
  { "runtimes": { "sysbox-runc": { "path": "/usr/bin/sysbox-runc" } } }
  ```
- 这台机器没有 systemd，用 `nohup dockerd > <日志文件> 2>&1 &` 启动。`docker info`：
  ```
  Storage Driver: overlayfs (driver-type: io.containerd.snapshotter.v1)
  Cgroup Driver: cgroupfs / Cgroup Version: 1
  Runtimes: io.containerd.runc.v2 runc sysbox-runc
  Default Runtime: runc
  ```

### 第 4 步：验证

#### 4a. `docker run --runtime=sysbox-runc --rm alpine uname -a`：失败

- 对照：默认运行时 `docker run --rm alpine uname -a` 正常：`Linux 2b68b3955f08 6.18.44-fc-v310 #1 SMP @0 x86_64 Linux`。
- sysbox-runc：
  ```
  docker: Error response from daemon: failed to create task for container: failed to create shim task:
  OCI runtime create failed: container_linux.go:439: starting container process caused:
  process_linux.go:405: getting the final child's pid from pipe caused: EOF
  ```
  sysbox-mgr、sysbox-fs 都收到了注册（`registered new container` / `Container pre-registration completed`），是 sysbox-runc 自己在起进程时死掉了。
- 绕过 Docker，用 `sysbox-runc --debug run` 直接跑同一个 alpine 的 OCI bundle，拿到真正的原因：
  ```
  level=fatal msg="update_oom_score_adj:358 nsenter: failed to update /proc/self/oom_score_adj: Permission denied"
  ```
- 根因：
  - sysbox-runc 的 `libcontainer/nsenter/nsexec.c`（约 745–752 行）**无条件**把容器 init 进程的 `oom_score_adj` 先设成 `-999`（sysbox issue #381 的做法），失败就 `bail` 退出。把 oom_score_adj 调低要 `CAP_SYS_RESOURCE`。
  - 这台机器上 root 的能力集是 `CapEff/CapBnd = 000001fffeffffff`，**第 24 位 `CAP_SYS_RESOURCE` 被从 bounding set 里去掉了**（`capsh --decode` 的列表里没有 `cap_sys_resource`）。实测 root 在 shell 里 `echo -500 > /proc/self/oom_score_adj` 也是 `Permission denied`，只能调高不能调低。
  - bounding set 里没有的能力，这台机器上任何进程都拿不回来，所以**官方的 sysbox-runc 在这里起不了任何容器**。普通 runc 不受影响，是因为 Docker 默认 `oomScoreAdj` 不往下调。

#### 4b. 试过的补救：自己编一个打补丁的 sysbox-runc（没有做成）

- 想法：只为确认"oom_score_adj 是不是唯一的障碍"，从 v0.7.1 对应的源码（sysbox 仓库 v0.7.1 标签固定的子模块：sysbox-runc `081856cc`、sysbox-ipc `f05151f4`、sysbox-libs `cacac193`，和官方二进制的 commit 一致）编一个测试用的 sysbox-runc，把 nsexec.c 里 `-999` 写失败时的 `bail` 改成只打警告（`git diff` 只有 4 行）。
- 编译要执行外部源码，超出了"装官方发布版"的范围，需要用户本人同意，所以停在了 `go build` 之前。
- 因为卡在第一步，**后面两项验证（容器里跑内层 dockerd + hello-world、确认用户命名空间）都没法做**。

### 结论

**这台机器不能用作 Sysbox 测试环境。**

- 卡在：sysbox-runc 起容器时无条件把容器 init 的 `oom_score_adj` 调到 -999，需要 `CAP_SYS_RESOURCE`；这台 Firecracker 虚拟机把这个能力从所有进程的 bounding set 里拿掉了（`CapBnd=000001fffeffffff`），root 也拿不回来。这是宿主环境的限制，不是 Sysbox 配置问题，没有配置项能关掉这一步。
- 次要问题（已绕过）：内核没有模块支持（没有 `/proc/modules`），sysbox-mgr 要 `--disable-shiftfs --syscont-mode=false` 才能起来，系统容器模式得按容器用 `SYSBOX_SYSCONT_MODE=TRUE` 打开。
- 好的一面：内核 6.18、idmapped mounts 和"overlayfs 叠在 idmapped mount 上"都支持（sysbox-mgr 自检都是 yes），FUSE 能用，sysbox-mgr 和 sysbox-fs 都能 Ready。换到一台普通的 Ubuntu 24.04 云服务器（有完整 root 能力、内核带模块、有 systemd），这两个问题都不会出现，测出来的结果也和生产一致。
- 后续：照约定请用户买一台 Ubuntu 24.04 小服务器当测试机（2026-11-08）。另一个办法是在云端会话里编上面那个只改了 4 行的测试版 sysbox-runc；即便跑通，也是"改过的运行时 + 非系统容器模式启动的 sysbox-mgr"，和生产环境差得比较多，只能当开发期的粗测。
